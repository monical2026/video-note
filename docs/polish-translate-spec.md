### 0.6 分段规则 v2（2026-08-28 用户参考规范定案，两层流水线，`src/services/segment.ts`）

> 原则：**分句**与**组段**分离；字符数/时长绝不作句子边界（人会说 25 秒长句，"Yes." 4 字符也是完整句），只作段落软限制；换段只落在已确认句尾，绝不句中强切；宁可多拼，不切半句。

**层 1 分句（碎行 → 句子，CUT/KEEP 优先级）**：
1. `>>` 说话人切换 → CUT；2. 真句尾 `.?!`（排除假句号：Dr./e.g./U.S. 缩写与 3.14/v1.2 小数）→ CUT；3. 弱边界 `,;:—…`/未闭合引号/续接词结尾 → KEEP；4. 下一条续接词开头（前无句号）→ KEEP；5. 其余一律 KEEP（保守）。
> ⚠️ 停顿候选断句（原第 6 条：gap≥1.5s + 新句开头三条件）已于 2026-09-02 按用户定案**移除**——用户判断其导致 [music] 等意外独立成段。已知代价：无字幕视频（Whisper 无标点转写）失去主要分句手段，将整段拼合（届时如需可再议恢复或替代方案）。

**层 2 组段（句子 → 阅读段落，软限制；2026-09-02 用户定案按 1~2 句调参）**：
段 <60 字符继续并；换段（任一）：下句是 `>>` / 句后停顿 ≥2.8s / **满 2 完整句即换** / ≥220 字符 / ≥18 秒；软上限 320 字符/20 秒只在下一个完整句尾换。参数常量在 `segment.ts` 顶部。

**条内预切与标记并段（2026-09-02 根因修正 + raw 取证精修）**：条内句号切开（补尾后再判片数——单切点条 "technical. As the" 是 json3 最常见形态，此前在补尾前判 ≤1 跳过导致句子从未建立、巨段）；`[laughter]`/`[music]`/`[clears throat]` 等纯非语言标记行并入前句不单独成段（前导标记并后句）；**判定前剥 `>>` 前缀**（YouTube 真实形态 `>> [music]`，否则整串匹配漏掉致独立成段）。

**短句并入优先于说话人分隔（2026-09-02 用户裁决）**：换说话人（`>>`）的强制换段受段落下限约束——段 <60 字符时即使下一句换人也继续并（"Hello." 5 字符不再独立成段）；段达下限后仍严格执行"不同说话人不合并"。

**AI 分段（暂停，`aiSegmentBreakpoints` 代码保留）**：大模型在句子级只输出断点句号（零改写、80 句/批、无效输出退回规则）。UI 按钮已于 2026-09-02 按用户要求移除（先聚焦规则分段逐步调稳，恢复时接线即可）。

**数据**：`TranscriptRecord.raw` 保留原始碎行（重新分段原料；原始数据永不丢）；重新分段文字一字不动、术语表保留、译文失配清空待重翻。

## 2. 润色规格 —— 英文原文侧（必须做）

> ⚠️ **v3 已作废（2026-08-27）**：润色功能整体移除，以下保留为历史存档。分段需求由 §0.6 程序化拼段承接（文字不改）。

1. **删除纯语气填充词**：um / uh / er / you know / I mean / right? 等
2. **修复断句**：把语音中的碎片化表达整理成完整句子，补足合理的主谓宾和标点
3. **按语义分段**：调整标点后分段——按意思合并相邻行成可读段落（一般 2~6 行一段），**不是**按语音停顿硬切、不把长句拆开；段落长短照顾屏幕阅读节奏，不要过长
4. **修正明显转写错误**：根据上下文修复 ASR 听错的英文单词、专有名词
5. **保留逻辑关系**：保留 but / so / because / for example（但是、所以、因为、举例来说）等真正推动内容的连接词
6. **保持语气**：尽量保留说话者的犹豫、强调、保留态度，但用更自然的文字表达

## 3. 润色规格 —— 红线（绝不做）

> ⚠️ **v3 已作废**（同 §2）；其中内容性红线已并入 §4 翻译指令。

- ❌ 不改变事实：数字、时间、人物、产品名和因果关系
- ❌ 不擅自补充原视频没说过的信息
- ❌ 不把「我不确定 / 可能 / 我认为」改成确定结论
- ❌ 不删除**有表达意义的重复**（如刻意强调 "very, very important"）
- ❌ 不删除真实情绪或态度（犹豫、讽刺、激动、道歉）
- ❌ 不把口语全改得过于书面——像论文或营销文
- ❌ 不擅自总结、缩写或删减信息（除非用户明确要求摘要）
- ❌ 不为了语句顺畅而合并**不同说话人**的内容
- ❌ 不把听不清的内容自行猜测为确定文本（标 `[inaudible]`）
- ❌ 不为了显得高级而换词

## 4. 翻译规格 —— 中文侧（v3.1 现行，2026-08-27 用户提供规范全文）

> 落点：`src/services/llm-translate.ts` 的 `llmTranslateBatch()` system 模板。以下为指令实际内容分层。

【通用基础规则】
- 完全匹配原文的语气和表达风格（口语保持口语，正式保持正式）
- 使用自然的中文句式——不要逐字按照英文语法翻译
- 不要翻译：专有名词、品牌名称、通常保留英文的技术术语（API、AI 等）、时间戳
- 保留原有格式标记（如项目符号）

【中文规则】
- 使用现代、口语化的简体中文。除非原文是正式风格，否则避免生硬的书面语
- 使用自然的中文句式——不要照搬英文语法结构
- 在决定最终中文表达之前，先理解完整的语义；不要因为源字幕被切分过，就机械地保留一个不完整的片段含义
- 使用"你"，除非原文明确使用正式敬语，否则不要使用"您"
- 面向聪明、熟悉科技和产品的用户来表达。像 AI、API、GitHub、Claude Code、Codex、skill、builder、deck 和 Chrome 这样的常见术语和产品名称，在自然情况下保留英文
- 中文与相邻的英文单词或数字之间加入易读的空格，例如"使用 Claude Code"和"过去 6 个月"
- 删除无实际意义的口头填充词，不要逐字翻译；但要保留真正表达的不确定性或强调语气

【事实红线】（沿袭）
- 不改变事实、数字、因果关系；不补充原文没有的信息
- 不把不确定表述改成确定结论；不删除有表达意义的重复

【术语表】（机制不变）
- 首次 LLM 翻译前 `extractTerms` 提取存库，每批注入，全片统一译法

【输出格式适配说明】：用户通用模板中"保留段落换行"在本插件场景下适配为"每条译文独立一行输出"——本插件逐段输入（单段无内部换行），行协议要求条内不换行（流式解析依赖）。语义无损。

> 免费通道（Google 免费端点）：机器翻译无风格控制，逐段直译——两种通道并存，入口不变（§0.4）。

## 5. 用户原始口述存档（2026-08-25）

> 保留原话以便追溯。含语音输入错别字，修正对照见 §5.1。

**口述原文（要做的事）：**

> 修复断句（将语音中的碎片化表达整理成完整句子，而不足合理的主谓宾和标点），调整标点后分段（按语义，而不是停顿切距长距拆开，形成可读的段落），翻译为自然中文，不逐字印反优先使用中文的自然清楚的说法；术语和人民一致，同一产品，同一人物技术术语全片保持统一译法；修正明显转写错误。根据上下文修复，然后asr听错的英文单词专有名词断句；保留逻辑关系，保留。但是所以因为举例来说等等，正在真正推动内容的连接词；保持语气，尽量保留受害者的犹豫，强调保留态度，但用更自然的文字表达

**口述原文（不做的事）：**

> 不改变事实数字、时间、人物产品名和因果关系，不擅自补充原视频没说过的信息，不把我不确定可能我认为改成确定结论，不删除有表达意义的重复，例如刻意强调，非常非常重要，不删除真实情绪或态度，例如犹豫讽刺激动道歉，不把口语全部改的过于书面相论文或营销文，不擅自总结缩写或删减信息，除非用户明确摘要明确，不为了语句顺畅而合并不重说话人内容，不把听不清的内容自行猜测为确定文本，不强制翻译所有因。文代码品牌名产品名AP模型通常应保留原文或复原文，不只按语法切字幕，字幕还需要按考虑观看节奏和屏幕阅读时间

| 7.7 | **润色重建 v4：一遍调用 + 段首锚定 + 批尾顺延**（2026-08-26 第四批，用户定案）：模型**整段重建**（上下文完整，不逐行清理），每段只**照抄一个起始行号**，段的覆盖范围由代码从相邻锚点推算（数数全在代码侧）；批尾未说完的话输出「行号\|»」顺延下一批（原文带回语境），分批切口只落在段落边界。费用与一遍调用完全相同 |
| 7.8 | **针对性修改纪律**（第四批）：改哪个功能只动哪处，旁发现问题记账不动手——用户明确要求（此前改流式时顺手换润色协议导致质量回归的教训） |

### 7.9 润色实现方式红线（用户口述原文收录，2026-08-26）

> 与 §3 的内容红线互补——这八条约束的是"怎么做"，§3 约束的是"做什么"。

1. 不要逐行翻译、逐行润色
2. 不要将平台字幕的换行当作句子或段落边界
3. 不要让模型一边计算 12–18 的范围、一边生成最终正文
4. 不要让模型输出一段无法映射回原始时间戳的"漂亮文本"
5. 不要先把碎句清理成看似正常的短句，再试图拼回完整意思
6. 不要仅依据字数、时间间隔或语义相似度合并；它们只能作为辅助信号
7. 不要把 but / because / so / that / which 等连接结构切断后单独翻译
8. 不要把不完整、听不清或低置信度内容硬润色成确定结论

### 7.7 实现事实（协议与参数变更）

- **输出协议从 JSON 改为行协议**（流式可读的前提，顺带消除长输出 JSON 截断嫌疑）：
  - 翻译：每行 `序号. 中文译文`（`parseNumberedLines` 解析，条数不符重试一次）
  - 润色：v4 起为每行 `行号|整段重建文本`（段首锚定，`parseAnchorLines` 解析 + `anchorsToSegments` 推算覆盖范围与顺延）；v3 的 `[from-to]` 区间协议已废弃（区间数行号是残句主因）
  - **术语表改为润色完成后独立小请求**（chatJson 非流式，输出小；失败不拖垮润色，返回空表）
- **流式链路**：`chatStream`（SSE 解析，`src/services/llm.ts`）→ `onStream` 回调（batch/batchTotal/累积文本）→ router `makeStreamBroadcaster`（**80ms 节流**，阶段/批号变化强制发）→ `LLM_STREAM` 广播 → 面板流式显示区（`.llm-stream`，自动滚到底）
- **max_tokens 显式 4096**（chat 与 chatStream；防服务端默认值过小截断长输出——「LLM 重翻无反应」问题的防御项之一）
- **TRANSLATE_BATCH_CHARS 6000 → 3000**（配合 4096 输出上限的安全预算）
- 错误条：`translateError` / `polishError` 两个状态，翻译/润色失败时显示在翻译栏下方

## 8. 待证据定位的开放问题（2026-08-25，等用户提供样本）

1. **润色段落质量不稳（DeepSeek 也有）**——头号嫌疑：LLM 数行号错位（让模型输出 [from-to] 区间需要精确计数，是其弱项；随机位置差与该假设吻合，批边界只能解释固定间隔的差）。等用户提交"特别不好"的段落样本验证后再改。

3. ~~**「用 LLM 重翻」零翻译**~~ **已闭环（2026-08-26 用户确认可用）**：根因为输出截断——max_tokens 显式 4096 + 翻译批 6000→3000 两防御项修复。
4. **智谱润色失败**——用户已确认 API 未充值（Coding Plan 与 API 余额是两个钱包互不相通）；待错误条文字确认具体原因。

拼段与复用的事实约束：
- 每段 `start` = 段首行时间戳，`dur` = 段内各行时长累加；点击行跳段首，高亮以段为窗口

## 10. 后续调整指南

- **段落太长/太短**：调 `segment.ts` 的三个常量（空隙 1.2s / 2 句 / 1200 字符）
- **翻译风格不满意**：改 §4 对应措辞 → `llmTranslateBatch()` 的 system 模板
- **术语译法不对**：改 `extractTerms()` 指令；可考虑后续做“用户自定义术语表”功能（未实现）
- **已知局限**：无标点 asr 的分段边界靠时间空隙+长度上限（未必总在最佳语义处，但永不破碎）；免费通道无风格控制
