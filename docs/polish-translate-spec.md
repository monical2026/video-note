# 逐字稿润色与翻译规格（v2）

- 日期：2026-08-25
- 状态：已确认、已实现（commit fcfab4c）
- 决策来源：用户逐条口述确认（原文存档见 §6）
- 用途：**润色/翻译标准的权威记录**——以后要调整效果，以本文档为基准改（怎么改见 §5）

## 1. 三项产品决策

| # | 议题 | 决策 |
|---|------|------|
| 1 | 逐字稿交互（单击跳转 / 划选记笔记 / 双击弹笔记） | **保留现状不改**（双击=浏览器选中一词，命中划选机制，属已知行为） |
| 2 | 翻译通道切换（免费翻过 → 想用 LLM 重翻） | **方案 A：手动「用 LLM 重翻」按钮**（点了才花 token；不自动重翻） |
| 3 | 润色分段粒度 | **按段展示**：一句一行 → 一段一行（时间戳/跳转/高亮以段为单位） |

## 2. 润色规格 —— 英文原文侧（必须做）

1. **删除纯语气填充词**：um / uh / er / you know / I mean / right? 等
2. **修复断句**：把语音中的碎片化表达整理成完整句子，补足合理的主谓宾和标点
3. **按语义分段**：调整标点后分段——按意思合并相邻行成可读段落（一般 2~6 行一段），**不是**按语音停顿硬切、不把长句拆开；段落长短照顾屏幕阅读节奏，不要过长
4. **修正明显转写错误**：根据上下文修复 ASR 听错的英文单词、专有名词
5. **保留逻辑关系**：保留 but / so / because / for example（但是、所以、因为、举例来说）等真正推动内容的连接词
6. **保持语气**：尽量保留说话者的犹豫、强调、保留态度，但用更自然的文字表达

## 3. 润色规格 —— 红线（绝不做）

- ❌ 不改变事实：数字、时间、人物、产品名和因果关系
- ❌ 不擅自补充原视频没说过的信息
- ❌ 不把「我不确定 / 可能 / 我认为」改成确定结论
- ❌ 不删除**有表达意义的重复**（如刻意强调 "very, very important"）
- ❌ 不删除真实情绪或态度（犹豫、讽刺、激动、道歉）
- ❌ 不把口语全改得过于书面——像论文或营销文
- ❌ 不擅自总结、缩写或删减信息（除非用户明确要求摘要）
- ❌ 不为了语句顺畅而合并**不同说话人**的内容
- ❌ 不把听不清的内容自行猜测为确定文本（标 `[inaudible]`）
- ❌ 不为了显得高级而换词

## 4. 翻译规格 —— 中文侧

1. **自然中文优先**：不逐字硬翻，优先用中文最自然、清楚的说法
2. **术语 / 人名 / 产品名全片统一译法**：同一产品、同一人物、同一技术概念从头到尾一个译名（机制：润色阶段产出术语表，存库，翻译每批 prompt 注入）
3. **代码、品牌名、产品名、API、模型名保留英文**（或「中文（英文）」形式），不强制翻译所有英文
4. 中文侧同样遵守 §3 全部红线

- 每段 `start` = 段首行时间戳，`dur` = 段内各行时长累加；点击行跳段首，高亮以段为窗口

## 7. 后续调整指南

- **效果不满意（太保守/太激进）**：改 `POLISH_SYSTEM` 里对应的“必须做”或“红线”措辞，重跑「重新润色」即可对比效果；本文档 §2/§3 同步更新
- **段落太长/太短**：调 prompt 里“一般 2~6 行一段”的表述
- **术语译法不对**：润色 prompt 的术语表产出规则在 `POLISH_SYSTEM` 末段；也可考虑后续做“用户自定义术语表”功能（未实现）
- **已知局限**（详见 ledger 验收期功能 13 minor）：润色分批无重叠上下文，跨批边界可能截断语义；术语表仅润色时产出，未润色的视频 LLM 翻译无术语表；免费通道润色后需手动点「翻译」
